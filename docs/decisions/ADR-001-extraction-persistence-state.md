# ADR-001 — Local extraction history and active state

Date: 2026-10-28  
Status: Accepted (Reviewed and approved by Antigravity; approved by Project Leader; merged via PR #4, commit `cd875b9`)  
Developer: Codex — Main Developer  
Reviewer: Antigravity — Independent Technical Reviewer / QA

## Context

TASK-006D requires validated extraction persistence and explicit re-extraction in
the existing SQLite repository layer. Approved A/B/C result models and canonical
schema 0.1 remain unchanged. This decision implements the task's approved scope;
it does not introduce an application extraction service.

## Decision

Add `document_extractions` using additive transactional `CREATE IF NOT EXISTS`
initialization. Existing source documents are preserved; initialization is
idempotent. Fields are extraction ID (UUID generated by the repository), document
FK, monotonically increasing per-document attempt number, payload JSON, extraction
status, active flag, UTC creation time, canonical schema version, optional method,
source hash, and optional successfully superseded extraction ID.

The database enforces unique document/attempt numbers, a unique partial index on
active document ID, valid statuses/active flags, FAILED remaining inactive, and
RESTRICT foreign keys for source/history references. Every managed connection
enables foreign keys and is explicitly closed. Existing unmanaged SQLite clients
must enable foreign keys on their own connections as required by SQLite.

`save_attempt` is allowed only without an active row. `replace_active` requires
the exact current active ID. Both require a matching source hash and expected
processing status, checked after BEGIN IMMEDIATE. No document-type or pipeline
readiness gate is invented here; orchestration and authorization belong to 006E
or its caller. A caller must capture these preconditions before processing.

The write transaction verifies SourceDocument and active state, validates the new
record, allocates its attempt number, deactivates the prior active row only for a
non-FAILED replacement, inserts the new attempt, updates SourceDocument metadata,
then commits. Every expected write rowcount must be one. Exceptions roll back and
close the connection, including exceptions at commit. Simultaneous writers are
serialized by BEGIN IMMEDIATE; the partial index remains a second invariant.

EXTRACTED and NEEDS_REVIEW can be active. FAILED is history only. Failed extraction
attempts preserve the previous active row, and have no `supersedes_extraction_id`
because they did not replace it. A database transaction that rolls back creates no
history entry. SourceDocument statuses describe the latest committed attempt,
while `get_active` explicitly returns the current usable result. An existing
active result always needs explicit replacement, including after a later FAILED
attempt. No automatic overwrite or history deletion is exposed.

History is ordered by attempt number, never wall-clock time or UUID. Source hash
is checked against stored SourceDocument metadata; persistence does not open or
rehash uploaded files. No source file is changed. SourceDocument status is a
latest-attempt summary, not a proof that the active result is complete or correct.

## Serialization

Reuse `InvoiceHeaderExtractionResult` (whose canonical Invoice can contain items)
and `InvoiceItemExtractionResult`. No alternate Invoice or InvoiceItem schema.
Strict persistence inputs and records forbid extra fields, and nested results are
revalidated from a detached Python-mode snapshot before writing. Explicit
non-null source IDs in fields/candidates must belong to the record's document;
cross-document aggregation is outside this single-source persistence contract.

Storage envelope version 1 identifies the result kind and tags candidate
`typed_value` scalars: Decimal, date, datetime, time, string, boolean, integer,
float, or None. This avoids the approved candidate union parsing JSON strings as
dates/datetimes or numbers. Canonical Decimal/date fields use their existing typed
schemas. Nonfinite numerics, unsupported types, unknown tags and malformed stored
data are rejected. Decimal strings preserve precision and exponent. Python
datetime/time ISO representations retain offsets, but do not preserve named
timezone objects or the ambiguous-time fold flag; neither is a canonical business
date requirement. No pickle, eval, dynamic imports or unchecked JSON is used.

Repository errors are static and do not log payloads, raw customer data, source
paths or SQL parameters. All data SQL uses bound parameters. Local database
storage contains document data and is not encrypted by this task.

## Alternatives

- Automatic overwrite: rejected because it loses explicit intent and history.
- Plain JSON round-trip of candidate unions: rejected because typed values can
  change type on deserialization.
- Parallel ORM/database or generic object serializer: unnecessary for V1 scope.
- Active status copied to latest metadata after FAILED: rejected because it would
  hide the technical failure; consumers instead use the explicit active API.

## Consequences and limitations

One document has zero or one active extraction, even when payload kinds differ;
this is not separate header/item slots. The future service must compose the
appropriate result before replacement. Active does not mean business-approved.
Existing schema initialization is additive, not a repair tool for arbitrary
corrupt or incompatible pre-existing tables. SQLite contention can return a safe
persistence error after its connection timeout; there is no background retry.
These APIs do not implement user authentication, orchestration, parsing, hosted
services, HTTP endpoints or downstream normalization/checks.
